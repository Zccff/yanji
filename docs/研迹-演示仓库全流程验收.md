# 研迹：用 Zccff/yanji-agent-lab 手动验收

这是一份你自己操作的清单。先做 1～8，再做记忆、评测和异常分支。每通过一项，记录页面截图、执行记录 ID、引用或 API 状态；模型回答文字可以不同，证据和结论应符合预期。

网页：<http://127.0.0.1:3001>。仓库：<https://github.com/Zccff/yanji-agent-lab>。

## 1. 连接、同步、自动项目索引

1. 打开协作工作台，选择 `Zccff/yanji-agent-lab`。已经存在时直接使用，保留现有数据。
2. 如果还没添加，点击“添加项目”：GitHub、Owner=`Zccff`、Repository=`yanji-agent-lab`，使用已经配置的 Token。
3. 等待初始任务完成。修复后的顺序是 **GitHub 数据同步 → 代码检出/分析 → 项目文档索引**，第一次连接不必额外抢先点击扫描。
4. 点击“刷新当前项目”获取完整演示资料。初次连接默认只抓少量数据，可能暂时看不到较早的 Issue 和故障 CI。
5. 再刷新一次，检查同一远端编号没有出现重复行。GitHub 新增数据时总数可以增加，不能仅以总数相等判断幂等。

预期：看到上表中的对象；同步完成后项目索引为 `ready`。当前这份演示代码曾扫描得到 **7 个文件、22 条索引记录**；代码或切片策略改变后数量可能变化。

需要核对接口时，在项目根目录的 PowerShell 执行以下只读命令：

```powershell
$labRepo = Invoke-RestMethod 'http://127.0.0.1:8000/api/repos' |
    Where-Object full_name -eq 'Zccff/yanji-agent-lab'
Invoke-RestMethod "http://127.0.0.1:8000/api/repos/$($labRepo.id)/memory-index/state" |
    Select-Object status, docs_total, docs_indexed, error_message
```

任务详情可在浏览器开发者工具 Network 中查看 `/api/repos/{id}/jobs/{job_id}`。同步结果应包含 `project_index.status=ready`。手动 `/memory-index/scan` 返回的是 `project.index` 持久任务的 `job_id`。

检查“工具调用过程”：应实际使用工作区读取或搜索工具。回答应区分当前 main 中的实现和 PR 分支中的改动。图谱页应看到这些函数或文件关系；图谱是轻量代码分析，不能据此断言有完整编译器级别的调用解析。

## 3. Issue 分析

1. 在右侧“项目资料 → Issue”打开 **#8**。
2. 点击“分析当前 Issue”（或在详情内重新分析）。
3. 查看流式过程、结论和证据。

也可以发送：

> 使用 issue-triage 分析 Issue #8：给出分类、优先级、复现条件，以及和历史 Issue #7 的关系。没有团队配置时请明确说明负责人证据不足。

预期：识别登录凭证过期的回归问题，解释 401/500，能够找到历史规则；不能凭空编造负责人。明确指定对象比“分析最新 Issue”更容易复现。

## 4. PR 审查：先测坏样本，再测好样本

在“项目资料 → PR”打开 **#12**，点击“分析当前 PR”。可以补充：

> 审查 PR #12 的分支差异，结合 Issue #8、行级 review 和该 PR 自己的失败 CI，判断是否可以合并。请区分当前 main 和 PR 分支。

预期：指出 `ExpiredTokenError` 没有正确捕获、过期凭证可能返回 500，结合失败测试给出阻塞理由。

然后对 **PR #10** 重复分析：应说明 Decimal、ROUND_HALF_UP 及新增边界测试，能解释 `2.675 → 2.68`。分析 **PR #11** 时，应关注数量正整数、单次 5 件上限和库存不被错误扣减。

“CI 成功”并不自动等于“可以合并”；还应检查审查意见、规则与证据完整性。

## 5. CI 排障与错误归因

依次选择三种失败运行，打开详情并运行分析：

| 运行 | 预期结论 |
| --- | --- |
| PR #12 所属分支的 Python CI | 关联 `lab/login-expiry-regression`，定位过期凭证的断言失败 |
| Failure lab / missing-dependency | ModuleNotFoundError，模块 lab_optional_gateway |
| Failure lab / simulated-timeout | 人为模拟 TimeoutError，独立演练 |

发送：

> 请先确认运行名称、分支和 commit SHA，再分析失败的 job、step 与错误日志。这个失败是否真的由 PR #12 引入？缺少关联证据请说明。

检查运行分支、SHA、测试名和日志引用。两个独立故障不能被归因为登录 PR。列表里同名的 Python CI 很多，选具体运行比“最新失败 CI”更可靠。

## 6. 上传文档、MQ、RAG 与引用

我已准备好上传文件：本项目根目录下 `docs/testing/lab-knowledge.md`。文件内容是虚构测试规则，没有真实凭据。

1. 进入“RAG 工作室”，选择演示仓库并上传这个文件。
2. 观察 `queued/processing → completed`、切片数量。小文件可能很快完成，可以打开 Network 查看上传响应中的 `job_id`。
3. 对同一文件重复上传，检查源记录、checksum 和活动任务是否被复用；系统可能展示复用提示。
4. 运行检索或问答，逐题检查来源片段，而不只看答案。

| 提问 | 预期答案 |
| --- | --- |
| DEVFLOW_LAB_POLICY_V1 的金额用什么类型、舍入方式？2.675 元是多少？ | Decimal、ROUND_HALF_UP、2.68 元 |
| 维护窗口、RTO 和 RPO 分别是什么？ | 周三 20:00～20:30，Asia/Shanghai；10 分钟、5 分钟 |
| 购买 6 件会扣减库存吗？ | 超过 5 件上限，返回业务错误，不扣库存 |
| 公司真实季度营收是多少？ | 资料不足，不能编造 |

在检索测试中对比 hybrid、vector、fulltext 和 rerank。先关闭过高的分数阈值排除阈值过滤，再调优；有结果后检查引用是否真的支持结论。

项目的自动“项目文档索引”用于 README/docs/清单等直接检索；这里的上传流程另外测试实际 Embedding、Milvus 和重排，两条链路要分别验收。

## 7. 多 Agent 计划与执行记录

在协作对话切换“计划模式”，发送：

> 联合分析 Issue #8、PR #12、该 PR 对应的 CI 和 ADR，判断 PR #12 是否可以合并。先生成计划，列出任务和依赖，等我确认后再执行，仅做分析。

1. 先看计划：是否有 PR 审查、Issue 分析、CI 排障、证据检索等与问题相关的任务。
2. 点击计划的执行按钮，观察 SSE 过程、任务状态和最终回答。

预期：证据指向同一个 PR/分支，综合结论应指出登录回归和失败 CI 的阻塞项。任务数量、工具顺序和重规划次数会随模型与证据而变；没有触发重规划不代表测试失败。

## 10. 记忆 CRUD、版本冲突、遗忘与衰减

1. 先完成至少一次聊天；在记忆工作台选中对应会话，点击“新增记忆”。
2. 新增一条虚构决策：事实键 `lab.acceptance.release`，内容“PR #12 修复前暂缓合并”。
3. 编辑成“修复后仍需人工核对 CI”，检查版本递增；展开版本历史，回滚旧版并检查产生新的修订。
4. 点击“遗忘”，筛选“已遗忘”后恢复。聊天原文应一直保留。
5. 要测版本冲突，在两个浏览器标签都打开同一条记忆的编辑框；先保存 A，再保存旧版本的 B。B 应提示版本已变，要求重新加载。
6. 设置半衰期为 1 天，观察“未来分数预估”。固定后不随时间衰减，但显式有效期仍生效。
7. 要实际等到期，可另建一条有效天数 **0.01** 的测试记忆（约 **14 分 24 秒**），到期后刷新并切到“已过期”查看。

有效条目的删除或到期影响的是自动记忆召回。原始聊天、版本记录，以及同一会话里仍在上下文窗口中的原话不应被物理删除；要验证新一轮自动记忆召回，请使用新的会话并明确区分“当前会话记忆”和“已晋升的项目知识”。

## 11. 固定评测与质量回归

本项目的 `docs/datas/evals/devflow-agent-lab.json` 已放入固定评测目录。先完成第 6 步上传，再打开“评估实验”：

1. 仓库选 `Zccff/yanji-agent-lab`。
2. 评测集选“DevFlow 演示仓库固定知识回归”（6 个问题）。若提示来源未就绪，先确认 `lab-knowledge.md` 已上传并完成入库。
3. 运行固定 RAGAS 评测，查看逐题工具、检索证据、回答、硬规则和 Judge 结果。
4. Judge 超时或报错应显示不完整，修复模型可用性后可重评分。
5. 改一次 Top-K 或重排设置，再跑相同评测集，比较两次结果。

这是调用真实模型的质量测试，会产生已配置服务的 API 用量。参考答案不等于跑出的分数；测试结束不等于全部质量指标达到阈值。

## 13. 内部错误分支：用受控测试，不强迫模型碰运气

网页操作可覆盖业务主链路，但难以稳定触发工具超时、最大步骤、溢出恢复、重复工具、Skill 权限拒绝等每个内部分支。从项目根目录运行：

```powershell
Push-Location backend
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m pytest app/tests -q -p no:cacheprovider --basetemp=../.data/pytest-manual-lab
Pop-Location
```

专门复验本次时序修复（真实 PostgreSQL、RabbitMQ、Worker、本地虚构 Git；不会修改演示仓库）：

```powershell
.\backend\.venv\Scripts\python.exe scripts/verify_project_index_pipeline.py
```

文档任务和同步的 MQ 幂等、错误分类测试：

```powershell
.\backend\.venv\Scripts\python.exe scripts/verify_rabbitmq.py
```

故障开关 `--faults` 会重启本项目 Worker 和 RabbitMQ，留到当前没有其他测试任务时再运行。Webhook 入站测试还需要 GitHub 能访问的 URL 与签名密钥配置，localhost 本身不可被 GitHub 直接访问。

## 记录结果

建议每项记一行：`步骤 / 输入或对象编号 / 工作流或任务 ID / 预期 / 实际 / 通过或失败 / 截图或引用`。遇到失败先保存 Network 响应或工具错误、时间和对象编号，再重试；这样可以区分业务规则、模型选择、权限和外网故障。
