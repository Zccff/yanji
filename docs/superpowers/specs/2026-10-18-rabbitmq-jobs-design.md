# RabbitMQ 文档入库与仓库同步

用户已确认接入两个流程，并要求幂等、有限重试、故障恢复和实际验证。按已有授权在当前会话直接实施。

## 架构

FastAPI 在 PostgreSQL 同一事务内保存业务记录和 BackgroundJob。BackgroundJob 同时承担持久化发送箱：Worker 的 dispatcher 将待发送任务投递至 RabbitMQ，收到发布确认后记录 published_at；发送失败保留记录等待重试。消费者只接收版本化的 job_id/kind，不接收凭据、文件正文或 ORM 对象。

Worker 与 API 是独立进程，复用现有文档和 GitHub 同步服务；文档仍保存在现有上传目录，API 和 Worker 采用相同工作目录。独立持久队列用于 document.ingest 和 repo.sync。消息持久化、发布确认、手动消费确认，终态任务重复投递直接确认。队列异常或进程退出允许至少一次投递，不宣称 exactly-once。

## 幂等与恢复

- 数据库唯一 active_key 合并内容相同的未完成任务；终态释放 active_key，允许之后主动刷新。
- PostgreSQL 会话级 advisory lock 串行化同一仓库的处理，进程退出自动释放；上传按仓库和 checksum 加锁，避免并发重复上传。
- 每次运行持久化尝试次数、可重试时间、错误、开始和完成时间。临时故障退避重试，默认最多三次；永久错误立即失败。失败消息投递死信队列。
- Worker 领取后崩溃，RabbitMQ 重投消息；dispatcher 还定期补投未完成任务，数据库终态和资源锁防止重复执行。业务提交后确认丢失也不会重复处理。
- 文档处理先按源文档分组清理旧切片和向量，再生成替代结果；重试不累加结果。删除与 Worker 使用相同仓库锁，处理中返回明确冲突；删除的排队任务取消。
- 同一仓库不同同步选项生成不同任务，但执行串行；相同选项的活动任务合并。凭据由 Worker 从当前仓库记录读取。

## 接口与前端

文档上传维持 HTTP 202，新增 job_id 等可观察字段；文档列表继续展示解析、切片、向量化阶段。重试接口重复调用复用活动任务，完成文档不重复处理。仓库同步返回 HTTP 202 与 job_id；连接仓库、手动同步、Webhook 和定时同步统一排队。新增仓库范围内任务查询接口，前端轮询到完成或失败再刷新业务数据；刷新页面可从 sync-status 恢复活动任务。RabbitMQ 暂不可用时已落库任务保留，不切回进程内执行。

主页面的旧 /knowledge/upload 入口也适配到同一持久文档入库流程；历史未创建源记录的文档仍按 checksum 识别重复，删除同步协调任务。Worker 对 PR/CI 子请求启用严格错误传播，代码检出附加步骤失败明确给出 warnings。
